# Dela 功能、技术与视觉设计分析

日期：2026-10-28  
对象：`Chang-Yo/Dela` 主分支与 `SJTU-Canvas-Helper-Android` 当前安卓端

## 结论

Dela 的优势不只是功能数量，而是它把功能放进了一套统一的本地工作台：数据同步进入 SQLite，Agent 通过 Skills 调用领域能力，界面通过同一套工作台、标签、预览、设置和通知规则消费这些能力。它的视觉高级感来自一致的设计约束和交互规则，而不是某个单独的组件或颜色。

你的安卓端在课堂学习闭环上更专门：录播、字幕、课件、截图提问、上下文保存、作业提交、移动端分屏和玻璃水池都更贴近学习过程。移植 Dela 时应移植它的基础方法，而不是把 Android 变成一个通用桌面 Agent。

## 四项功能的迁移复杂度

复杂度按“安卓端真正可用、可持久化、可处理断网和权限失败”的完整功能计算。工作量是熟悉当前项目的单名开发者粗估，不包含真实学校账号验收、接口变化、设计评审和发布流程；只做演示页面会低很多，但不计入产品完成度。

### 邮件

Dela 邮件不是一个简单的“打开网页邮箱”。它包含约束完整的同步系统：账号和密码进系统加密存储，邮件夹和消息落 SQLite，IMAP 增量同步，HTML/MIME 解析，草稿和回收站有本地语义，SMTP 发信，后台同步和通知也要处理。

安卓端如果直接使用同样方案，需要增加：

1. Android 后台同步任务与电量策略。
2. IMAP 长连接或周期同步的生命周期管理。
3. MIME、HTML、内嵌图片和附件安全处理。
4. 邮箱密码或应用专用密码的加密保存。
5. 通知点击后能准确回到邮件和文件附件。

可行的安卓第一版应只有：收件箱、已读状态、搜索、邮件正文、附件下载和“用系统分享/打开”。写信、草稿、回收站和多账号放到第二阶段。

### 全局搜索

Dela 的全局搜索实现其实很克制：它主要查询已经缓存的数据，不在搜索动作中临时下载全部 Canvas 文件；搜索结果按类型限制数量，然后跳转到对应页面。它没有把所有聊天正文强行放入一个巨大索引，聊天主要按标题搜索。

安卓端可做成：

```text
搜索入口
  ├─ 课程与作业
  ├─ Canvas 文件名与已准备正文
  ├─ 字幕与课堂时间点
  ├─ 笔记
  ├─ AI 会话标题和用户问题
  └─ 邮件主题/发件人/摘要（接入邮件后启用）
```

结果必须带来源、课程、时间点和打开动作。正文索引只收录已经缓存或已经解析过的内容，避免用户点搜索后触发大量网络请求。

预计复杂度：中等，约 1 个数据索引层、1 个统一搜索 UI、每个来源一个适配器和跳转协议。它是四个功能中最值得先做的一个。

### 课表与待办

Dela 的待办不是简单复制 Canvas `/users/self/todo`。它根据 Canvas 课程和作业同步本地待办，因为交大实例的 Canvas planner/calendar 数据可能为空。待办对象有来源、课程、截止时间、完成状态、已读状态、通知时间和本机自定义字段。

安卓端已有作业、截止日期、提醒和本机日程，因此不需要从零重做。建议增加统一数据模型：

```text
TodoItem {
  id, source, courseId, assignmentId,
  title, notes, dueAt, status,
  calendar, color, readAt, syncedAt
}
```

视图只做两个：列表和月历。Canvas 作业与本机待办使用同一个条目组件，但写入权限分开：Canvas 作业状态来自同步，本机待办可以自由编辑。

### 水源社区

Dela 的水源功能本质上是一个受限的 Discourse 客户端，并且明确把它作为试验能力。它包含授权、话题列表、分类、搜索、话题正文、回复、发帖、私信、收藏/个人列表、图片和未读通知。这个功能的难点不是页面，而是授权方式、接口稳定性、HTML/媒体安全、通知轮询和用户数据边界。

安卓端若要做，建议分三步：

1. 只读话题搜索和正文阅读。
2. 收藏、个人列表和链接回跳。
3. 回复、发帖、私信和通知。

第一步仍然属于高复杂度，但可以控制在独立模块，不影响 Canvas 主流程。不要把水源内容默认注入 AI 上下文，必须由用户明确选择。

### 文档能力

Dela 的文档读取和界面预览是两条路径：Agent 读取用独立 document-reading Skill，GUI 预览使用独立的 PDF/Office 组件。这样可以分别控制模型上下文和视觉预览，不会为了让 AI 读文件而强行把整个 Office 引擎塞进主界面。

Dela 的文档 Skill 还明确处理：

- 文档准备任务和 jobId。
- 输入副本和输出文件的临时目录清理。
- PDF 文字层、扫描页图片、按页读取。
- Word、PowerPoint、Excel 正文与表格。
- 解析警告和 `needs_visual_read` 状态。
- 释放任务，避免临时文件长期残留。

安卓端不应照搬“嵌入 Python 运行时”路线，原因是 APK 体积、ABI、启动时间、后台进程和升级复杂度都会明显增加。更合适的路线是：

1. 继续使用现有 Rust 解析器读取文字层和结构。
2. 增加每种格式的 `DocumentEvidence` 结果，区分正文、表格、图片页、警告和覆盖范围。
3. PDF 继续按页渲染图片，用户指定页码时按需发送视觉模型。
4. PPTX 继续优先平台切片；本地只做文字结构和图片页兜底。
5. 解析结果按账号、文件版本和会话缓存，避免退出对话后重复提取。
6. 明确告诉模型和用户“已读取哪些页、哪些内容没有读取”。

### 源码规模信号

对 Dela 当前源码做的只读统计可以帮助判断复杂度：邮件主进程约 9 个文件/2447 行，邮件界面约 14 个文件/3070 行；全局搜索主进程约 342 行、界面约 283 行；待办主进程约 419 行、界面约 1298 行；水源主进程约 1257 行、界面约 2949 行；文档主进程约 963 行，文档 Skill 与脚本另有独立运行时。行数不是质量指标，但能说明邮件和水源不是加一个页面就完成，搜索则明显适合先落地。

## Dela 为什么显得更高级

### 1. 它先定义规则，再做页面

Dela 的开发文档把工作台规则写成了不变量：打开目标由统一函数决定，预览标签组内只有一个，编辑/双击/拖动/保留后才变成常驻标签；设置页只展示已经实现的操作；瞬时反馈用浮窗，持久状态用页面内提示，高频操作直接内联。

你的安卓端目前更多是“每个页面把功能做出来”，不同页面各自决定按钮、卡片、提示和弹窗。功能已经很多，但用户要重新学习每个页面的操作方式，所以视觉上会显得零散。

### 2. 它只有一套视觉语言

Dela 使用统一的 `beautiful-ui` Token 和组件基座，颜色、圆角、阴影、动效、按钮、图标按钮、切换、滑杆、Toast 都共享同一套语义。它还明确删掉没有使用的组件，避免组件库越来越杂。

你的安卓端同时存在：

- MUI 主题覆盖。
- `demo/src` 手写响应式 CSS。
- 页面级 `sx` 样式。
- 自定义卡片、按钮、弹窗和播放器控件。
- 多套图标和不同圆角规则。

这会造成“每个页面都不难看，但放在一起不像一个产品”。尤其当前主题中按钮默认使用极圆的胶囊形，很多卡片和弹窗又使用不同的圆角、边框和阴影，导致控件层级不够清晰。

### 3. 它把强调色留给真正重要的动作

Dela 的颜色语义主要是：墨色正文、低对比背景、细边界、单一品牌 accent、红色错误。普通按钮不抢视觉，主按钮只用于当前页面最重要的动作，状态使用颜色点或轻量徽标表达。

你的安卓端当前 crimson/ivory 主题有识别度，但主色、卡片底色、按钮底色和提示色经常同时出现，页面第一眼不容易看出“现在最应该点什么”。

### 4. 它用空白和层级代替装饰

Dela 的高级感主要来自：

- 页面标题和正文之间有明确层级。
- 内容区宽度受控，不把信息铺满整屏。
- 卡片只包住一组有关系的内容。
- 边框比阴影更常用。
- 圆角用于容器，不是所有文字按钮都做成胶囊。
- 图标按钮没有文字时必须配 Tooltip 或可理解的图标语义。
- 重要操作集中在一行或固定底部，不让按钮散落在内容里。

### 5. 它的交互是可预测的

用户在 Dela 里看到文件、会话、邮件或课件时，点击、双击、拖动、右键和“在旁边打开”的行为有统一含义。标签、分组、预览和常驻状态也是统一的。

你的安卓端需要借鉴这个思想：同一个对象无论从课程、资料库、录播课件还是 AI 上下文打开，都应该遵守同一套“预览、继续、扩大、返回、收藏、提问”的行为。

## 安卓端视觉重构方案

### 第一层：建立自己的设计 Token

不直接复制 Dela 代码，先建立安卓端自己的语义 Token：

```text
surface.canvas       页面背景
surface.panel        一级面板
surface.card         卡片
surface.raised       浮层
ink.strong           主标题
ink.default          正文
ink.muted            次要文字
line.subtle          细分隔线
accent.primary       主操作
accent.soft          选中/提示背景
status.success       已完成/已连接
status.warning       待处理
status.danger        错误/删除
radius.control       控件圆角
radius.card          卡片圆角
radius.sheet         底部面板圆角
shadow.card          卡片阴影
motion.fast          点击反馈
motion.enter         页面进入
```

所有 MUI 组件、手写 CSS、播放器控件和 AI 面板都只使用这些 Token。以后改主题只改 Token，不逐页改色。

### 第二层：收敛组件

先做 10 个共享组件：

1. `AppSurface`：统一页面面板。
2. `SectionHeader`：标题、说明和右侧动作。
3. `PrimaryAction`：当前页面唯一主操作。
4. `QuietIconButton`：静默图标按钮，统一 Tooltip、触摸区域和按下反馈。
5. `StatusPill`：只用于状态，不用于普通按钮。
6. `SegmentedControl`：筛选、列表/日历、字幕/课件等互斥选项。
7. `InlineNotice`：持久错误、同步状态和权限提示。
8. `Toast`：短暂成功、失败和后台完成提示。
9. `PreviewSheet`：文件、课件、截图的统一小框/扩大层。
10. `ActionMenu`：课程、文件、作业和对话的二级操作。

完成后逐步替换页面内重复的 Button、Card、Modal 和 IconButton，而不是一次性重写所有页面。

### 第三层：统一布局

手机端：

- 顶部只放页面标题和一个上下文动作。
- 底部导航最多保留 4–5 个一级入口。
- 搜索、筛选、更多操作进入同一条工具栏。
- 详情页使用明确的返回按钮和底部主操作区。
- 课件、AI、字幕和文件预览使用统一的 Bottom Sheet/全屏层。

平板端：

- 侧栏只放一级导航。
- 内容区采用“列表 + 详情”或“视频 + 课件”两栏。
- 第二栏切换时第一栏保持状态。
- 右侧 AI 面板只在用户打开后占位，不永久压缩主内容。

### 第四层：统一反馈

- 网络加载：骨架屏或局部加载，不用整页转圈。
- 后台任务：底部任务条或轻量 Toast。
- 登录过期：页面内横幅 + 明确的重新连接动作，不弹重复窗口。
- 失败：说明失败对象、原因和下一步，不只显示“失败”。
- 成功：短 Toast 或局部状态变化，避免每次都弹大对话框。
- 空状态：说明“为什么为空”和“下一步能做什么”。

## 迁移顺序建议

### P0：先做视觉基础和全局搜索

复杂度：中等，收益最高。

- 建立 Token。
- 建立共享组件。
- 把当前课程、资料、AI、录播和作业页面统一到同一套按钮和面板。
- 新增跨课程搜索，先搜索已缓存数据。

### P1：统一待办和课堂转写

复杂度：中高。

- 把作业和本机日程统一成 TodoItem。
- 增加列表/月历切换。
- 增加全课字幕搜索、时间跳转、转写保存和导出。

### P2：文档证据缓存与可解释阅读

复杂度：高。

- 统一 PDF、DOCX、PPTX、XLSX 的解析结果。
- 保存文件版本、读取范围、页码和警告。
- 对话重新进入后复用已经准备好的结果。
- 视觉模型只收到用户要求的页面图片。

### P3：邮件只读版

复杂度：高。

- 先收件箱、搜索、正文、附件。
- 后续再加写信、草稿、回收站、多账号。

### P4：水源只读版

复杂度：高。

- 先授权、话题列表、搜索、正文阅读。
- 暂不做发帖、私信、通知和 AI 自动调用。

## 许可证和实现边界

Dela 主项目使用 GPL-3.0-or-later，不能直接把 Dela 的业务代码复制进当前 MIT 安卓项目后继续按 MIT 发布。可以借鉴它的产品规则、数据模型和交互方式；视觉设计 Token 需要自己重新实现。Dela 仓库中的 `beautiful-ui` 目录标注来自 MIT 项目，但 Dela 自身的适配代码、业务模块和整体组合仍需单独做许可证审查。

最稳妥的做法是：

1. 只参考 Dela 的公开行为和架构。
2. 继续使用当前项目已有的 MUI、React 和 Rust/Kotlin 结构。
3. 自己实现一套 Dela 风格的 Token 与组件，不复制 Dela 业务代码。
4. 先做搜索和视觉基础，验证移动端体验后再决定邮件和水源。
